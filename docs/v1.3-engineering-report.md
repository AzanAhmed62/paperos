# PaperOS v1.3 engineering report

**Release:** PaperOS 1.3.0+4
**Application ID:** `dev.paperos.app`
**Schema:** version 2 (unchanged from v1.2)
**Report date:** 11 November 2026
**Status:** implementation and automated verification complete. Partial runtime
validation was performed on a physical OnePlus 6T (Android 11, API 30); the
remaining device cases and production signing are still open.

This report records what was actually built, tested, analysed, and audited. It
does not convert a compile or a unit test into a device pass.

## Objective

v1.3 turns the v1.2 reading environment into a launcher with a deterministic
navigation hierarchy:

- formal Level 0 Home, Level 1 primary surfaces, Level 2 child surfaces and
  Level 3 Android/system surfaces;
- Android Back follows the PaperOS hierarchy and is consumed on Home;
- HOME, LAUNCHER and `ACTION_VIEW` intents are distinguished;
- the task/activity lifecycle tolerates cold start, warm start, duplicate
  launches and process recovery;
- the app drawer gains recents, favourites, stable ordering, refresh, system-app
  visibility and honest restricted/empty states;
- Home gains quick actions, pinned apps, date/density preferences and launcher
  status;
- navigation, Back, shell-state, router-recovery, intent and launcher-service
  tests are added;
- the release remains offline-first with no `INTERNET` or broad storage
  permission.

The v1.2 architecture is preserved: `StatefulShellRoute.indexedStack`, five
destinations, Riverpod, GoRouter, existing overlays/readers/library/backup, and
the same application ID.

## What changed

### Navigation and Back

- Added `lib/app/paper_back_policy.dart`: a pure `decidePaperBack` function with
  four outcomes (`popOverlay`, `popFilesFolder`, `goHome`, `consume`).
- Rewrote `lib/app/router.dart` around `appRouterProvider` and
  `createAppRouter()`. Each router gets its own root navigator key and is
  disposed with its provider.
- Added one shell-level `PopScope(canPop: false)` in `PaperShell`. Home is
  terminal; Back never finishes the activity.
- Destination switching uses `StatefulNavigationShell.goBranch`, preserving each
  branch's navigator and scroll state. No `context.go` replacement was applied
  wholesale.
- Moved the Files folder stack from widget state into `filesBrowseProvider`, so
  the shell can inspect and pop folder depth.
- Exposed the destination bar as `PaperDestinationBar` with explicit
  `currentIndex` and `onSelect`.

Exact Back order:

1. a Level 2 root overlay (reader, note editor, app drawer, Tasks, Search) closes;
2. a Files folder step pops; the location root is itself a step;
3. a non-Home primary surface returns to Paper Home;
4. Paper Home consumes the gesture.

The full contract is in [`navigation-architecture.md`](navigation-architecture.md).

### Android launcher lifecycle

- Added `SystemIntentChannel.kt`, which classifies `MAIN+HOME`,
  `MAIN+LAUNCHER` and `ACTION_VIEW`.
- `MainActivity` now passes the cold-start intent to both `FileBrowserChannel`
  and `SystemIntentChannel`, forwards warm intents through `onNewIntent`, and
  disposes the new channel with the engine.
- Added `lib/core/platform/system_intent_service.dart` and
  `lib/app/system_intent_controller.dart`.
- `SystemIntentController` resets HOME/LAUNCHER traffic to Paper Home and clears
  the Files stack and drawer search. VIEW traffic stays with
  `ExternalOpenController`, so a cold-start PDF import is not raced by a reset.
- `PaperApp` drains pending intents and refreshes the HOME-role status on resume.
- `ExternalOpenController` uses the provided router instead of a global.
- The HOME-role request now uses `startActivityForResult` rather than
  `startActivity`. Android's permission controller reads the caller through
  `getCallingPackage()`, which is only populated for the result-bearing launch;
  a plain launch makes the dialog fail silently with "Package name cannot be
  null". This was found and fixed during the physical-device run.

Manifest launcher attributes were audited rather than changed arbitrarily:
`singleTask`, `taskAffinity="dev.paperos.app"`, `stateNotNeeded=true`,
`clearTaskOnLaunch=false`, `excludeFromRecents=false`, and
`enableOnBackInvokedCallback=true` are retained and documented.

### Launcher UX and settings

- `AppCatalogSnapshot` now carries a `restricted` flag beside the app list.
  `PlatformLauncherService` reads it from the native reply; `AppCatalogCache`
  stores it.
- The drawer adds pinned and recent shortcut strips, pin/unpin on rows and
  shortcuts, pull-free explicit refresh, stable ordering, system-app visibility,
  real icons (or initials), a restricted banner/notice, and graceful empty
  states.
- Recents are stored in the existing `shared_preferences` settings document,
  capped at eight package names. No second settings database was added.
- `LauncherActions` owns launch-plus-recent recording, favourite toggling,
  clearing recents, refreshing the catalogue, and HOME-role flows.
- Home adds four quick actions (Search, Apps, New note, New task), a pinned-app
  row, optional date under the clock, comfortable/compact density, launcher role
  status and a launcher-settings shortcut.
- Settings adds Home date/density, HOME-role status and request, refresh apps,
  show icons, show system apps, show recents, clear recents, and a pinned-app
  editor.
- There is no separate launcher text scale. The existing interface text scale
  remains the single accessibility control; density changes spacing, not type
  size.

### Catalog and provider correctness

- `installedAppsProvider` selects only `showSystemApps` and
  `favoritePackages`, so recording a recent does not reload and flash the list.
- `visibleAppsProvider` is now a synchronous `Provider<AsyncValue<...>>` derived
  from the cached catalogue, so searching and pinning re-order immediately
  instead of showing a loading state.
- `favoriteAppsProvider` and `recentAppsProvider` do not subscribe to the
  catalogue when their lists are empty. This avoids a Riverpod
  "setState during build" regression in shell tests and avoids an unnecessary
  package scan on a Home screen with no pins.

### Device validation

A physical OnePlus 6T (`ONEPLUS A6010`, Android 11 / API 30) was connected
during a follow-up run on 11 November 2026. The debug build
(`dev.paperos.app.debug`, version 1.3.0+4) was installed and exercised:

- installed and launched; the five destinations and Paper Home rendered;
- Library → Back returned to Paper Home; Back on Paper Home was consumed and the
  activity stayed alive;
- the app drawer enumerated 45 launchable apps with real icons, and pinned,
  recent, pin/unpin and clear-recents behaviour worked;
- launching Authenticator from the drawer worked, and the recent entry survived
  a force-stop and relaunch;
- warm `MAIN+LAUNCHER` and `MAIN+HOME` intents delivered while Settings was open
  both reset the hierarchy to Paper Home;
- repeated launches reused one task and one `MainActivity` instance;
- force-stop and relaunch returned to Paper Home;
- the HOME-role confirmation dialog now appears after the
  `startActivityForResult` fix. The dialog was cancelled, so the role was not
  changed;
- Settings displayed `PaperOS 1.3.0 (4) · schema v2`.

Two behaviours were observed and are expected rather than defects:

- When a search or composer field is focused, Android delivers the first Back to
  the IME; the overlay closes on the next Back. This is Level 3 system behaviour.
- The app drawer's search field autofocuses, so the keyboard opens with the
  drawer. This is pre-existing v1.2 behaviour and was left unchanged.

Still not exercised on Android:

- actually confirming the HOME role and replacing the launcher;
- pressing the system Home button while PaperOS holds the role;
- a warm HOME/LAUNCHER intent delivered by a real launcher (the run used
  `am start` with the same intent filters);
- duplicate tasks created by a real launcher/OEM (the run verified one task
  after repeated `am start` calls);
- process death while a reader is open;
- predictive-Back preview (Android 11 does not provide it);
- SAF folder grants and Files folder Back;
- `ACTION_VIEW` document import from another app;
- native PDF rendering, backup transfer, E-Ink appearance and keep-screen-on.

The full 48-case checklist in `manual-testing.md` remains the release gate.

## Release readiness

**Automated readiness:** yes. The code analyses cleanly, all 202 tests pass, the
debug APK builds, and the unsigned release artifact has the expected package,
version and permission set.

**Distribution readiness:** no. The 11 November 2026 run on a physical OnePlus 6T
(Android 11 / API 30) covered the core launcher and Back paths, but two gates
remain:

1. **Remaining device validation.** Confirming the HOME role and replacing the
   launcher, the system Home button while the role is held, warm intents from a
   real launcher, duplicate tasks on a specific OEM, process death while a
   reader is open, predictive Back, SAF folder grants, `ACTION_VIEW`, and native
   PDF/backup/E-Ink/keep-screen-on remain unverified. The full 48-case checklist
   is still the release gate.
2. **Production signing.** No owner keystore or credentials were supplied. The
   default release task still fails closed; only an unsigned analysis APK was
   produced.

The core launcher, app-drawer and Back paths are device-verified on one Android
11 device. No release note should describe the remaining items above, the full
manual checklist, or a signed release as complete until those checks are done.

## Commit recommendation

The changes are coherent and self-contained. Recommended commit after review:

```text
feat: ship PaperOS 1.3 launcher navigation and app drawer

- formalize Home / primary / child / system navigation levels
- make Android Back follow PaperOS and consume it on Home
- harden HOME/LAUNCHER/VIEW intent handling and task lifecycle
- add app drawer recents, pins, refresh and restricted states
- add Home quick actions, layout preferences and launcher status
- add navigation, intent, launcher and widget tests
- bump to 1.3.0+4 and document the navigation architecture
```

Leave the working tree uncommitted until the owner reviews it. Do not push
without an explicit request.

## Known limitations and unverified items

- The HOME-role dialog was device-verified, but the role was cancelled.
  Confirming the role and actually replacing the system launcher were not
  exercised.
- Warm HOME/LAUNCHER resets were verified with `am start` using the same intent
  filters, not with a real launcher. Duplicate-task and OEM task-affinity
  behaviour is not device-verified.
- Predictive-Back visual behaviour is not device-verified; Android 11 does not
  provide the preview.
- Process death while a reader is open, SAF folder grants and Files folder Back,
  `ACTION_VIEW` import from another app, native PDF rendering, backup transfer,
  E-Ink appearance and keep-screen-on remain unverified.
- App-drawer enumeration was verified on one Android 11 device (45 apps,
  including real icons and launches). The restricted flag remains a heuristic
  (`resolved.size <= 1`) and may flag a genuinely tiny app list.
- When a text field is focused, Android delivers the first Back to the IME; the
  overlay closes on the next Back. This is expected Level 3 behaviour.
- There is no automated Android instrumentation harness.
- Production signing is blocked by missing credentials.
- Backups remain unencrypted and unsigned.
- v1.2 device-only paths remain unverified.
