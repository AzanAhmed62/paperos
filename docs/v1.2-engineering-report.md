  content path.
- No debug signing fallback for production release.
- No committed secrets or keystores.
- No fabricated device test results.

### 3.4 Environment constraints

- No Android device or emulator was attached.

## 6. E-Ink profile

### 6.1 What the profile changes

The E-Ink Friendly profile is a user preference, not a device-detection result.
It is stored as `display.profile` in the settings envelope and is included in
backups.

| Area | Standard | E-Ink Friendly |
| --- | --- | --- |
| Motion | 220 ms theme/overlay transitions | Zero-duration route overlays, sheets and dialogs; `MediaQuery.disableAnimations` true |
| Home clock | Rebuilds every second | One-shot timer just after the next minute boundary |
| Reader flow | Stored paged/scroll choice | Forced to paged at render time; stored choice unchanged |
| Page turns | Stored tap/swipe/both choice | Forced to tap zones at render time |
| Page-turn zones | 30% each side | 34% each side, wider selection-safe centre |
| Reader chrome | Auto-hides after inactivity | Stays visible once summoned |
| Typography | Stored font size, line height, margins | Render-time ×1.06 font size, +0.06 line height, ×1.12 margins, clamped |
| Touch targets | 44/32 logical pixels | 48/40 logical pixels |
| Contrast and selection | Paper palette, 20% selection fill | Higher contrast, 34% selection fill |
| Loading | Indeterminate spinner | Static quarter ring |
| Scrolling | Platform fling and overscroll decoration | Drag still works; lift-off fling and overscroll decoration disabled |

### 6.2 Where it is applied

- `PaperApp` watches `displayPolicyProvider`, applies the high-contrast palette,
  publishes `DisplayPolicyScope`, and sets `MediaQuery.disableAnimations`.
- `router.dart` reads `navigationDuration` from the policy scope.
- `PaperScrollBehavior` is installed at the app root.
- Home schedules the clock with `nextClockDelay` and reschedules on profile
  change.
- `ReaderController`/`ReaderScreen` apply `readerSettingsForDisplay` to a copy;
  adjusted values are never written back to Settings.
- Shared `Paper` widgets use the larger targets and static progress ring.
- Settings shows the active profile and an honest capability summary.

### 6.3 What it does not do

- It does not change Android system UI, the status bar, the keyboard or other
  apps.
- It does not control a front light or refresh waveform.
- It does not guess an e-ink panel from a device model.
- It does not claim a vendor flash.

## 7. Backup and restore

### 7.1 Format and contents

A `.paperosbackup` is a plain ZIP containing:

- `manifest.json` with format/version, app/schema versions, counts, entries,
  warnings and library byte count;
- `manifest.sha256` for corruption detection;
- `database.json` for documents, progress, locators, bookmarks, annotations,
  notes, tasks, folder grants and related metadata;
- `settings.json` for the settings envelope, including the display profile;
- `books/` for document payloads;
- cover files when present.

Books are stored as files, not as SQLite blobs. The manifest and per-entry
SHA-256 values detect corruption and casual modification; they are not a
signature and do not authenticate the archive author.

### 7.2 Validation and limits

- Document count: 10,000.
- Entries: 20,050.
- Per-entry size: import limit plus 16 MiB.
- Total uncompressed size: 8 GiB.
- Metadata JSON: 64 MiB each.
- Manifest: 4 MiB.

Preview enforces the document/metadata caps before the user can commit. The
producer enforces entry/document/total-size limits before writing. Restore
validates ZIP structure, entry names, duplicate names, directories, symlinks,
encryption flags, compression methods, declared and actual sizes, counts,
checksums, JSON shape, table/column allowlists, types, ranges, identifiers,
foreign keys, SQLite integrity and file relationships before committing.

### 7.3 Restore sequence and rollback

1. Inspect the archive and show a preview.
2. Create a safety snapshot in app-private `safety/` storage.
3. Extract payloads into disposable staging under flat sequence names.
4. Validate the archive and every relationship.
5. Copy attachments into the library area.
6. Replace the database in one transaction.
7. Commit settings.
8. Delete staging only after a successful commit.

The `committed` guard prevents cleanup from deleting newly copied files after a
successful commit. Copy failure removes partial copies. A damaged payload,
missing attachment, future format or path traversal is rejected before the live
library changes. The settings write and SQLite commit still cannot share one
transaction; a process kill between them is a documented cross-store window, and
the safety snapshot is created before it.

### 9.2 Signing

Release signing is fail-closed. Credentials are read, highest priority first,
from:

1. `-Ppaperos.keyProperties=...` or individual Gradle properties;
2. `PAPEROS_KEY_PROPERTIES` or individual `PAPEROS_*` environment variables;
3. the traditional untracked `android/key.properties`.

The debug keystore is never used for a release build. If credentials are absent,
`assembleRelease` and `bundleRelease` throw a Gradle exception. The only escape
hatch is an explicit analysis build:

```bash
flutter build apk --release -Ppaperos.allowUnsignedRelease=true
flutter build appbundle --release -Ppaperos.allowUnsignedRelease=true
```

That path produces an unsigned, non-installable, non-distributable artifact.
Flutter writes the APK under `app-release.apk`; it must be renamed to
`app-release-unsigned.apk` immediately so it cannot be mistaken for a release.

`android/key.properties.example` documents the expected keys. `key.properties`,
`*.jks`, `*.keystore` and `*.p12` are ignored. No signing secret is tracked in
the repository.

### 9.3 Build optimization and audit

- Release builds use R8 minification and resource shrinking.
- AOT snapshots are produced per ABI.
- Split-ABI APKs are supported for size analysis.
- The merged release manifest is inspected, not just the source manifest.
- `apksigner verify` is run on the actual artifact.
- The release checklist requires a signed rebuild and a fresh audit after owner
  credentials are supplied.

## 16. Recommendations

1. **Supply owner signing credentials and rebuild.** Use the untracked
   `android/key.properties` or `PAPEROS_*` environment variables. Verify the
   certificate with `apksigner` and confirm the release task fails without
   credentials.
2. **Run the 36-case manual checklist on a physical phone.** Prioritise install,
   EPUB import/read/resume, PDF rendering, SAF import, backup/restore, annotation
   export, text selection, process death and responsive layout.
3. **Run the E-Ink subset on a real e-ink device.** Record ghosting, refresh
   latency, selection visibility, chrome persistence and font scaling. Do not
   claim hardware refresh.
4. **Measure runtime performance on target hardware.** Capture startup, frame
   timing, memory, EPUB pagination latency, PDF page latency and SAF throughput;
   add the results to `docs/performance-report.md` with device details.
5. **Keep the manifest audit as a release gate.** Re-audit every signed artifact;
   do not reuse the unsigned hashes.
6. **Treat backup encryption as a future format decision.** If added, use a
   mature reviewed library and standard KDF/authentication, never custom crypto.
7. **Use the debug APK for development only.** It is debug-signed, includes
   `INTERNET` for Flutter tooling, and is not a substitute for device validation
   or release evidence.
8. **Do not add new reading features before the device gate.** The roadmap
   already places device validation first; keep it there.

## 18. Final verdict

PaperOS 1.2 is **code-complete and automation-verified**, with the v1.2
reliability, E-Ink, backup/restore, annotation-export and release-engineering
work implemented. The release artifact was built, measured and statically
audited, and the automated suite passed 163 tests with a clean analyzer and
formatter.

It is **not Play-release-ready yet**. Two gates remain external:

- **Production signing is Blocked** because no owner keystore or credentials were
  supplied. The repository correctly fails closed instead of falling back to
  debug signing.
- **Physical-device validation is Blocked** because no Android device or emulator
  was attached. All 36 manual cases remain not run, including SAF transfer, PDF
  rendering, EPUB touch selection and E-Ink appearance.

Hardware E-Ink refresh is **Not implemented** by design; the software profile
does not claim to flash a panel. Backups are **Not implemented** as encrypted or
signed files; the documentation states this plainly.

The correct next step is not another feature. It is to supply the owner key,
rebuild and verify a signed artifact, then run the manual checklist on a phone
and an e-ink device. Until then, the unsigned APK/AAB are analysis artifacts, not
a release.
